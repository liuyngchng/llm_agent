# AI 客服工作流文档

## 1. 概述

### 1.1 定位

本工作流是一个面向城市燃气公司的智能客服系统，基于 Dify 平台运行，能够自动识别用户意图并路由到对应处理分支，覆盖燃气泄漏紧急处理、账单查询、业务办理、故障维修、综合咨询五大场景。

### 1.2 整体架构

```
┌──────────┐      ┌──────────┐      ┌──────────┐
│   用户    │ ───→ │     服务 │ ───→ │   Dify   │
│ (微信/APP │ ←─── │ (业务层)  │ ←─── │ (工作流)  │
│  /网页)   │      └──────────┘      └──────────┘
└──────────┘                              │
                                     ┌────┴────┐
                                     │ RAGFlow │ (可选，知识库增强)
                                     └─────────┘
```

- ** 服务**：接收用户消息，调 Dify Workflow API，返回结果给用户
- **Dify**：执行工作流——意图分类、知识库检索、Agent 调度、结果聚合
- **RAGFlow**（可选）：替代 Dify 内置知识库，提供更高质量的文档解析与检索

## 3. 组件详解

### 3.1 Begin

| 属性 | 值 |
|------|-----|
| 模式 | conversational（多轮对话） |
| 欢迎语 | "您好！欢迎致电城市燃气客服中心。我是您的智能助手，请问有什么可以帮您？" |
| Prologue | 开启（用户首次进入时自动发送欢迎语） |

### 3.2 Categorize（意图分类器）

使用 LLM 对用户输入进行意图识别，从 5 个类别中选择最匹配的一个。

| 类别 | 路由目标 | 触发示例 |
|------|----------|----------|
| **Gas Leak & Emergency** | Agent: Emergency Handler | "我家闻到煤气味"、"燃气报警器一直在响" |
| **Bill & Payment** | Retrieval: Bill KB | "查一下这个月燃气费"、"怎么交费"、"为什么账单这么高" |
| **Service Application** | Agent: Service Application | "申请开通燃气"、"过户给新房主"、"想暂停用气" |
| **Repair & Maintenance** | Retrieval: Repair KB | "燃气灶打不着火"、"热水器不出热水"、"预约安检" |
| **General Information** | Retrieval: FAQ KB | "营业厅在哪里"、"现在气价多少"、"冬季用气注意什么" |

**配置参数：**

| 参数 | 值 |
|------|:--:|
| LLM | deepseek-v4-pro |
| 温度 | 0.1 |
| 分类策略 | Precise（精确匹配） |
| 记忆窗口 | 1（每次独立分类） |

### 3.3 五条处理分支

#### 分支 ①：燃气泄漏 / 紧急处理

| 属性 | 说明 |
|------|------|
| **路由** | Categorize → Agent（直接，无知识库） |
| **为什么不用知识库** | 紧急情况需要立刻给出安全指引，不能因检索延迟耽误时间 |
| **记忆窗口** | 6 轮 |

**Agent 执行逻辑：**

```
第 1 步：立即输出安全指引
  ├── 立即关闭燃气阀门
  ├── 打开门窗通风
  ├── 不要开关任何电器
  ├── 不要使用明火
  └── 迅速撤离到安全地点

第 2 步：多轮收集关键信息
  ├── 用户姓名
  ├── 联系电话
  ├── 具体地址（精确到楼栋和房间号）
  └── 泄漏情况描述（燃气味浓淡、持续时间等）

第 3 步：告知预计到达时间，确认抢修队已调度
```

#### 分支 ②：账单与缴费

| 属性 | 说明 |
|------|------|
| **路由** | Categorize → Retrieval: Bill KB → Agent: Bill & Payment |
| **Retrieval 用途** | 检索缴费方式、阶梯气价、账单周期、滞纳金政策 |
| **记忆窗口** | 12 轮 |

**Retrieval 检索配置：**

| 参数 | 值 |
|------|:--:|
| top_k | 1024 |
| top_n | 8 |
| 相似度阈值 | 0.2 |
| 混合检索权重 | 0.7 关键词 / 0.3 语义 |

**Agent 内置知识（System Prompt 嵌入）：**

| 项目 | 内容 |
|------|------|
| 缴费方式 | 微信/支付宝、银行代扣、营业厅现金、网上银行 |
| 账单周期 | 每两个月抄表，抄表后 3 个工作日出账单 |
| 阶梯气价 | 一档 0-300m³ 2.8元 · 二档 300-600m³ 3.36元 · 三档 600m³+ 4.2元 |
| 滞纳金 | 逾期每日 0.05% |

> **注意**：以上价格为示例，上线前需替换为当地实际气价。

#### 分支 ③：业务办理

| 属性 | 说明 |
|------|------|
| **路由** | Categorize → Agent（直接，多轮收集） |
| **为什么不用知识库** | 业务办理是信息收集型对话，不是知识问答 |
| **记忆窗口** | 6 轮 |

**支持的业务类型：**

| 业务 | 需收集的信息 | 费用说明 |
|------|-------------|----------|
| 新装燃气 | 户主姓名、身份证号、地址、电话、房屋面积、用气设备 | 初装费 2800元 |
| 燃气过户 | 新户主姓名、身份证号、电话、房产/租赁证明 | 手续费 50元 |
| 迁表/改管 | 户号或地址、改造需求、电话 | 按实际改造量计费 |
| 暂停/恢复用气 | 户号、户主姓名、电话、原因 | — |

**办理流程：** 提交申请 → 1-3 个工作日审核 → 工作人员联系确认上门时间

#### 分支 ④：维修与保养

| 属性 | 说明 |
|------|------|
| **路由** | Categorize → Retrieval: Repair KB → Agent: Repair & Maintenance |
| **Retrieval 用途** | 检索故障排查步骤、维修流程、费用标准 |
| **记忆窗口** | 12 轮 |

**常见故障处理：**

| 故障 | 远程排查步骤 | 远程无法解决时 |
|------|-------------|---------------|
| 燃气灶打不着火 | 检查电池 → 清洁火盖 → 检查阀门 | 记录户号，安排师傅上门 |
| 热水器不出热水 | 检查水压 → 检查电源 → 检查燃气供应 | 记录户号，安排师傅上门 |
| 燃气表异常 | 记录户号，直接上门检修 | — |
| 管道/阀门漏气 | **升级为紧急情况** | 转抢修队立即处理 |

**报修收费：** 上门费 50元 + 材料费/工时费另计 · 年度安检免费

#### 分支 ⑤：综合咨询

| 属性 | 说明 |
|------|------|
| **路由** | Categorize → Retrieval: FAQ KB → Agent: General FAQ |
| **Retrieval 用途** | 检索营业网点、价格政策、安全知识、投诉流程 |
| **记忆窗口** | 12 轮 |

**咨询范围：**

- 营业厅地址、营业时间、联系电话
- 燃气安全知识、冬季用气注意事项、一氧化碳中毒预防
- 居民/非居民气价、阶梯价格政策
- 开户/过户/销户流程、所需材料
- 投诉建议记录

### 3.4 VariableAggregator（变量聚合器）

将 5 条分支的输出汇聚为一个变量：

```
answer = Agent:Emergency@content
       | Agent:Bill@content
       | Agent:Service@content
       | Agent:Repair@content
       | Agent:General@content
```

**工作原理：** 运行时只有被 Categorize 选中的那条分支有实际内容，其余为空。聚合器取非空值传递给 Message。

### 3.5 Message（最终输出）

输出变量：`{VariableAggregator@answer}`

将聚合后的 Agent 回复返回给用户。

## 4. 全局配置

| 配置项 | 值 | 说明 |
|--------|:--:|------|
| LLM 模型 | `deepseek-v4-pro@default@DeepSeek` | 所有组件共用 |
| 默认温度 | 0.1 | 低温度确保客服回答稳定、一致 |
| 默认 Top P | 0.3 | — |
| 默认 Max Tokens | 512（Agent）/ 256（Categorize） | Agent 需要更多输出空间 |
| 检索 top_n | 8 | 每次返回最多 8 条文档片段 |
| 检索 top_k | 1024 | 初筛 1024 条 |
| 相似度阈值 | 0.2 | — |
| 混合检索权重 | 0.7 关键词 / 0.3 语义 | 偏向关键词匹配，适合客服场景 |

## 5. 知识库配置

导入 Dify 后需要创建以下 3 个知识库，并将 `kb_id` 替换为实际值：

| 知识库 | 占位 ID | 建议内容 |
|--------|----------|----------|
| 账单支付知识库 | `gas-bill-payment-kb-001` | 缴费方式说明、阶梯气价表、账单周期、滞纳金政策、发票开具流程 |
| 故障维修知识库 | `gas-repair-troubleshoot-kb-002` | 常见故障排查手册、报修流程、收费标准、安检流程 |
| 综合 FAQ 知识库 | `gas-general-faq-kb-003` | 营业网点信息、燃气价格、安全知识、业务办理流程、投诉渠道 |

> **知识库优化建议：** 如果文档量大且格式复杂（PDF、扫描件、表格），建议用 RAGFlow 替代 Dify 内置知识库。Dify 通过 HTTP 节点调 RAGFlow 检索 API 即可。

## 6. 部署流程

### 6.1 前置条件

- Dify 平台（开源版 `docker compose` 部署或云服务版）
- 服务（用于对接用户端，调 Dify API）
- LLM API Key（DeepSeek 或其他兼容 OpenAI 格式的模型）
- 知识库文档准备完成

### 6.2 部署步骤

```
第 1 步：部署 Dify
  ├── git clone https://github.com/langgenius/dify.git
  ├── cd dify/docker
  ├── cp .env.example .env
  ├── 编辑 .env，填入 LLM API Key
  └── docker compose up -d

第 2 步：导入工作流
  ├── 打开 Dify 控制台 → 创建应用 → 导入 DSL
  └── 上传 csm_test.json

第 3 步：创建知识库
  ├── 在 Dify 中创建 3 个知识库
  ├── 上传文档（PDF/Word/TXT/Markdown 等）
  └── 将知识库 ID 填入工作流对应的 Retrieval 节点

第 4 步：发布
  └── 点击 Publish → 获取 API endpoint

第 5 步：Go 服务对接
  └── POST /v1/workflows/run
      Headers: Authorization: Bearer <api-key>
      Body: { "inputs": { "sys.query": "用户消息" }, "user": "user-id" }
```
